# Agent operational checks

The console's **Agent health** panel and authenticated `GET /api/operations` report shared service state plus the responding runtime's local progress. `/api/status` includes the same report. Reports identify instanceId and the per-boot runtimeId; each condition has a shared or instance scope. `pnpm sre:health` reads the running service using SRE_SERVICE_URL and SRE_API_TOKEN; add `--strict` for a nonzero exit status unless that report is healthy. The offline `sre:ready` command inventories configuration and credential presence before startup.

Readiness reports the selected credentialMode and missing variable names without their values. It chooses a present static token first, otherwise OAuth when configured; Jira basic uses its email/token pair. OAuth issuer URLs must have the supported HTTPS structure. It applies runtime's shared load-time validator and normalized defaults, including a Teams tenant supplied through TENANT_ID, without mutating the input. core.runtimeConfigurationValid concerns that validation, not database connectivity or provider permissions. A configured credential mode remains unverified until the corresponding live operation succeeds. The strict CLI rejects invalid service profiles, missing configured Eve settings, missing core values and enabled-reader/writer setup.

`pnpm sre:ready --json --strict` includes a separate rollback entry. When rollback is enabled, its own selected write credentials, enabled repository reader, protected ref and GitHub workflow configuration must be present. Reader OAuth cannot satisfy the writer entry. Placeholder account labels in an explicit retryScope, or in the selected OAuth issuer's retryScope, remain incomplete; absent optional labels are allowed and retain per-client waits. Disabled rollback can be staged without write credentials. This is offline inspection: it never tests a workflow, branch protection or write permission and always leaves liveValidated false. The separate read-only access command continues to exclude writer clients.

`pnpm sre:check --live` tests [individual read operations](INTEGRATIONS.md#operation-specific-read-checks), including complete recent/active inventories, configured metric windows, immutable repository source and review/CI access. A metadata read alone no longer passes a repository's access check. Missing smoke resources stay unverified; partial results stay incomplete. JSON output uses --json and never contains source text or provider response bodies. Exit 0 means all required configured-resource read contracts passed, with endToEndValidated still false. Exit 1 indicates a failed probe/configuration and exit 2 indicates incomplete, unverified or unconfigured coverage. The command excludes rollback, model and message clients.

The running report has three states:

| State | Evidence |
| --- | --- |
| starting | Provider checks are still within startup grace, or a current incident assessment is queued/running |
| healthy | No tracked agent condition requires attention at the observed time |
| needs-attention | A polling, work-queue, loop, delivery, or rollback condition requires investigation |

An active auction incident continues to appear under Investigations. Agent health measures the investigator and its delivery/monitoring paths. Both reports retain their own evidence requirements; healthy fixture operation does not establish live vendor access or production recovery.

## Conditions

- Enabled Dynatrace, ServiceNow, GitHub/GitLab and log readers require recent complete shared checkpoints and a recent complete read on the responding instance for the current configuration scope. Its own reader failure is visible immediately, even after a healthy peer refreshes the shared checkpoint. Missing initial reads or mismatched checkpoint scope are reported after startup grace. On-demand Jira reads are outside the scheduled-poll requirement.
- Metric monitors additionally require a recent valid source sample. Error checkpoints retain the last successful read, so operators can see the gap.
- Exhausted investigation retries, old queued work, and unreclaimed expired leases are visible. An operator can resume exhausted analysis with an audited retry. Uncertain external writes still require their own reconciliation.
- An active incident with no current audited assessment and no queued/running investigation needs attention. The health API identifies an affected incident and the console opens it directly. A queued replacement review keeps shared health waiting until its assessment is published; accepting the question alone does not produce a recovery notice. Exhausted work retains its separate manual-retry condition. Resolved historical cases are outside this active-review check.
- Failed/unknown Teams deliveries with unhandled current follow-up, and delayed live deliveries, require attention. An [operator inspection](DELIVERY-INSPECTIONS.md) can record manual follow-up without changing transport status; new evidence or a restore generation reopens review. Pending messages in the offline profile are expected while its sender is off.
- Unknown dispatches, expired rollback leases, and dispatched rollbacks lacking independent verification beyond the configured wait are visible. Workflow submission is not a health proof.
- Tick/poll loop errors and stalled or missing progress are visible. Notice-persistence failures appear in the API. An operational notice's own uncertain delivery stays visible without generating an endless series of notices.

`GET /health` remains the small database/HTTP liveness check. A downstream polling fault does not remove webhook ingress from service. An external supervisor should inspect `/api/operations` through the operator network and alert separately; an agent cannot guarantee its own Teams delivery while its process, database, or Teams transport is unavailable.

## Log scope limits

A log monitor evaluates at most 100 active region/release scopes. If its query finds more, that monitor remains incomplete and publishes none of those overflowing scopes. Health reports the affected service/monitor and asks for a narrower source query. The limit is a bound on local evaluation, not a measured provider quota or a production capacity target.

Independent monitors on that service and other configured services still evaluate. The existing investigator can process queued read-only work and Teams commands, while the investigation loop continues to report the scope-limit failure. A full explicit `tick` rejects before its protected action phase. This exception applies only to the host's classified scope-limit condition; storage/cache-integrity failures and unexpected errors still stop the investigation path. Restore holds retain their existing behavior.

Accepted raw read receipts and deduplicated counters remain durable. An incomplete polling evaluation retains its previous successful cursor; rejected admission metadata remains visible alongside a scope-limit failure. Review the source filter and service mapping with its owner rather than raising the limit by assumption. When the bounded samples expire, the loop can recover, but sample expiry or quiet logs do not resolve the business incident. See [proactive log thresholds](CASEWORK.md#proactive-log-thresholds).

## Teams notices

Operational observation runs every ten seconds when the scheduler is enabled. Connected mode with live Teams queues an operational notice on a meaningful condition change and one notice after the reported conditions clear. Unchanged conditions and increasing ages/counts do not repeat the notice. State and outbox intent commit in one transaction; a storage failure leaves the notice retryable. No external message is sent in the offline profile.

Notification state has two owners:

| Scope | Owner and recovery |
| --- | --- |
| Shared service | Source checkpoints, monitoring data, persisted queues, uncertain writes and the restore hold. Same-scope peers deduplicate these notices in the database. A starting peer with pending source inventory cannot announce recovery merely because its startup grace has not expired. |
| Instance | Provider read failures or missing/stale local reads, invalid metric samples, clock drift and tick/poll loop failure, stalled progress or missing progress. Only the reporting runtime can clear its notice. A healthy peer cannot announce recovery for it. Instance notices include the configured label and a short runtime ID. |

Set SRE_INSTANCE_ID or the root instanceId configuration field to a useful 1–128 character label using letters, digits, dot, underscore, colon or hyphen. It defaults to the operating-system hostname. Runtime IDs distinguish separate processes sharing that label. Healthy starts do not create a per-boot notification row. A replacement runtime does not certify recovery of a crashed runtime's old local fault; use the independent supervisor to observe process loss and replacement. This endpoint does not aggregate peer-local health into a fleet report.

Notification scope version 2 uses new durable keys bound to service, tenant, environment and destination; local keys also bind the runtime ID. Older combined checkpoints remain historical and are not used to fabricate a recovery. An ongoing fault can generate a first notice in its new scope after upgrade. Shared recoveries say Shared service checks recovered; local recoveries name the reporting instance. One does not imply that all other scopes are healthy.

The native PostgreSQL exercise verifies two actual agent processes producing two local fault notices, their two matching recoveries, one concurrently deduplicated shared fault and one shared recovery. A separate case uses the production GitHub read client with synthetic HTTP responses: one instance's HTTP 401 remains visible while the healthy peer's API reports healthy; only its own successful read clears the local fault. It queues records in the private database and sends no real Teams messages. Live provider authorization and Teams delivery still require tenant acceptance.

Shared source state answers whether recent complete data exists for the service. Local read state answers whether this process has recently read it successfully. The latter is held in memory and starts unproven on every boot; a shared success cannot certify a new runtime's credentials. Source errors remain available in shared audit metadata, but a failed peer cannot erase a newer successful cursor or toggle a shared data-availability warning while that data is fresh. Concurrent checkpoint updates lock and merge the current row in one transaction. A changed scope cannot inherit the old scope's success.

Integration badges use the same operational report. **Recent read** means a complete recent read on this instance, with valid recent monitor samples where configured. **Starting** awaits its first read; **Needs attention** includes its source-specific conditions. **Configured** describes an on-demand reader whose permissions have not been established by scheduled polling. Credential presence and another runtime's successful read do not establish those permissions. Authentication/response diagnostics omit provider-controlled response text.

Set `teams.operationsConversationId` to an allowlisted operational conversation. If exactly one conversation is allowlisted, it is the default. Multiple destinations require an explicit choice. The bot needs a saved, enabled conversation reference for the matching service and tenant. The observer never selects an arbitrary incident thread or a foreign tenant. If the reference is missing or access has been removed, the API still exposes the conditions for an external monitor.

Every notice is an outbox record and uses the existing authenticated Teams sender. Unknown delivery outcomes require reconciliation before a manual retry. Browser and unit fixtures do not establish tenant consent or installation.

## Database upgrades at startup

At startup, older ServiceNow aggregate lifecycle states are reconstructed as individual ticket states from the retained source audit. Every migrated incident receives one audited, read-only investigation for its new revision, including an identity-only upgrade that leaves status and start time unchanged. The upgrade, audit and queued review commit together; a storage failure leaves the legacy state available for retry. Reopening an already migrated database does not enqueue the review again. Existing event bodies, sessions and saved tickets remain intact. Planning waits for the new review; prior action approvals do not become current merely because the agent restarted.

## Current assessments and waiting work

The incident API reports `assessmentStatus`: `missing`, `unverified`, `outdated` or `current`. It matches the displayed assessment body to its retained review record and compares incident revisions. The database retains the full audit; the console shows up to five recent reviews. Matching uses the full audit, including when several records have the same timestamp. A newer review observed during the context read cannot certify an older displayed snapshot. This describes review coverage of recorded incident evidence; it does not certify provider freshness, production recovery or model accuracy. The console identifies an outdated or unaudited reply even when no pending job remains. Ask a question to request a fresh investigation; an exhausted job still uses the audited retry procedure below.

Fix-ticket drafting and rollback controls wait for a current review. Runtime rollback eligibility also requires a current audited assessment before proposing or dispatching, including after an earlier approval. New evidence can therefore block a queued rollback before its provider read or deployment transport. The worker evaluates eligibility for its newly computed draft against the revision it investigated; publication still fences that revision before any persisted result becomes current.

The existing single-worker queue orders ready work by eligibility time. A pending job uses `next_at`; an abandoned running job becomes eligible when its lease expires. A stale question or required reply is requeued at its new eligibility time, so it yields to already waiting incidents and questions. Original creation times remain in the audit, and retry backoff still applies. Coalescing retains waiting reply destinations and leaves explicit questions separate. This repairs fairness within the local queue; it does not implement the proposed distributed dispatcher or guarantee response latency under an overloaded worker.

## Resume an exhausted investigation

If a workflow alert's original thread is still waiting for its first diagnosis, exhausted work queues a short **Investigation needs attention** notice there. It records the observed failure time, exact failed job/attempt, a bounded redacted error excerpt and the existing `retry` command. It describes that failed attempt, not the cause of the incident. The diagnosis remains pending and can be answered by later successful work. Other joined groups with their own unanswered workflow alerts receive their own scoped copy; completed recipients do not receive another exhaustion notice.

The host queues at most one notice per unanswered incident/thread/source promise. A queued, simulated, sent, failed, discarded or uncertain copy does not make repeated failures safe to resend. Inspect uncertain delivery through the existing delivery workflow. Leaving, uninstalling or changing sharing access prevents a new notice; a manual rejoin does not revive a cancelled promise. The failure audit and notice intents are atomic, but delivery remains a separate result. No new feedback is queued during a restore hold, and releasing that hold does not replay a historical failure notification. The local rules/mock tests do not establish native Microsoft receipt or actual-model quality.

If a fresh result is committed while failure feedback is still queued, the matching feedback becomes **discarded** with a reason pointing to the replacement reply. Its original text and failure history remain available. A delivery claimed before that commit rechecks the promise before transport preparation; a completed or cancelled promise can retire that unsent claim too. Expired or already prepared/submitted sends keep the existing uncertainty and inspection rules. The replacement being queued does not prove it reached Microsoft or was read, and an assessment does not verify incident recovery. Simply requesting another investigation does not suppress a still-relevant failure explanation.

After inspecting and correcting the cause, select the incident and use **Retry investigation** with a reason. The console shows the failed job, attempt count/error, replacement status, and recent operator retry history. The original job becomes `retried`; its error and attempt count remain intact. A new job starts at zero attempts with the original question and current incident evidence, in the same durable issue session. A telemetry-triggered retry becomes an explicit operator request so routine coalescing cannot discard it.

The CLI provides the same operation:

```sh
pnpm sre:retry <incident-id> <failed-job-id> "Read access restored; inspect current evidence"
# If the response was lost, reuse the request ID printed by the CLI:
pnpm sre:retry <incident-id> <failed-job-id> "Read access restored; inspect current evidence" --request-id <saved-id>
```

An authenticated API client sends `POST /api/incidents/<incident-id>/jobs/<job-id>/retry` with `{ "requestId":"stable-unique-id", "reason":"Actual reason" }`. The job must belong to that incident/service and be `dead`. The receipt, new job, preserved old attempt, operator evidence, and incident revision commit together. Repeated identical requests return the same receipt/replacement; changed content or a pending/running/done/retried target returns 409. Out-of-scope jobs return 404. Storage failure returns 503 and leaves the transaction uncommitted; retain the request ID on retry. A replacement that exhausts its own retries needs a separate operator request, preserving the chain.

In an allowed Teams conversation, send `@SRE Agent retry <incident-id> <job-id> <reason>`. Passive responder text cannot invoke it. The authenticated responder ID, tenant, conversation, and reason enter the audit. API audit records use of the shared operator credential; they do not identify the person who used it. Loopback mode records a local operator identity. Teams commands interrupted by storage failure retain their durable command lease and resume after expiry, including a failure after the retry action committed but before its acknowledgement was saved.

This operation enqueues read-only investigation. It does not reset Teams delivery status, dispatch/retry a rollback, approve a proposal, or resolve an incident. A later investigation still uses current evidence and the existing recovery/approval gates. The console/API retain up to 40 work/retry rows per incident, with exhausted work prioritized; the database retains the complete audit.

## Polling and metric configuration

`pollConcurrency` defaults to 4 and allows 1–8 concurrent source/metric tasks. A slow reader no longer serializes every independent source behind it. All active tasks drain before the tracked poll finishes, including a database failure in another lane, so shutdown can wait safely.

Each Dynatrace/ServiceNow instance additionally reconciles the active inventory at startup and every five minutes by default. A peer's inventory read does not bypass this instance's permission check. This increases inventory request volume with the number of instances; validate query cost and permissions in the tenant. `activeReconcileIntervalMs` supports 10000–86400000 ms. Partial inventories leave that read incomplete while retaining accepted recent events and any newer successful peer cursor. Configuration changes invalidate old checkpoint health; use a new service key for actual tenant/environment/service changes. See [startup reconciliation](INTEGRATIONS.md#startup-and-active-issue-reconciliation) for query contracts and scope limits.

Metric selectors must yield one aggregated series with paired numeric values and timestamps. The last `consecutive` samples must be finite, strictly increasing, within the fifteen-minute query window, within `maxSampleGapSeconds`, and no newer than the requested end time. The newest sample must satisfy `maxSampleAgeSeconds`. Duplicate, reordered, stale, future, missing, or unpaired data never counts as a healthy window. Threshold/name changes create distinct event identities while retaining the monitor's issue identity.

### Provider delays and pagination

Reads make at most three transport attempts per API call. A Retry-After delay longer than three seconds ends that call instead of blocking the polling lane. The connector retains the provider deadline and rejects subsequent calls before authentication/transport until that deadline passes, including a delay received on the final attempt. HTTP-date delays and GitHub quota reset timestamps use the configured clock; connected PostgreSQL runtimes supply database coordination time. Without an advertised usable delay, HTTP 403/429 receives a conservative one-minute hold. Short permitted waits honor cancellation. Ordinary transient server errors retain bounded backoff. Deployment writes are submitted at most once; a write held before transport is classified as not submitted, while an error after submission stays uncertain.

GitHub also observes exhausted quota headers on successful responses. It keeps that accepted result and records the advertised reset before allowing another request; pagination cannot report completion when a later page is deferred. The [GitHub header contract](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) defines x-ratelimit-remaining and the UTC epoch-second x-ratelimit-reset. This successful-response interpretation is enabled for the GitHub adapter; other provider and OAuth success headers need their own verified contracts. Missing or malformed GitHub reset/delay metadata uses a bounded one-minute fallback. An expired valid reset does not create a fresh hold. A longer Retry-After or existing wait wins.

Without an explicit runtime retryScope, these waits belong to the connector object. Configured shared buckets persist committed deadlines through process replacement; see the coordination details below. Clock/storage failure while retaining a response observation blocks further requests from that client until it can retain the observation. If a write was already submitted, the lost result remains uncertain and requires reconciliation. Already in-flight requests cannot be recalled by a later quota response. Use provider quotas and fleet-level request budgeting when validating the actual account. The [GitHub rate-limit guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#handle-rate-limit-errors-appropriately) describes error-response handling. Deferred reads leave the instance requiring attention and retain the last complete cursor; a new complete read is required for recovery.

OAuth acquisition additionally shares one pending request among concurrent readers and retains token-endpoint retry deadlines by issuer/client ID within its provider object. Credential changes invalidate the cache, and a late response from the former configuration cannot authorize its waiting caller. A resource HTTP 401 drops only the matching cached token for a subsequent independent request; deployment writes remain subject to their original submission and approval boundaries. See [OAuth configuration and response budgets](INTEGRATIONS.md#oauth-reader-configuration). Teams SDK authentication has its own lifecycle.

Caller cancellation releases its authentication waiter. Remaining readers continue; when all readers leave, the helper aborts and discards the abandoned acquisition. Cancellation is checked after final preflight as well, so a request cancelled before the submission boundary makes no deployment call. An interrupted submitted request still needs its existing outcome reconciliation. See [authentication cancellation](INTEGRATIONS.md#cancellation-around-authentication-and-submission).

GitHub/GitLab numeric pagination checks Link rel=next and GitLab x-next-page, including empty/short pages. It increments the original configured route and filter, without sending credentials to a supplied continuation URL. A same-origin repository-ID alias is accepted only as an indication of the next numeric page. Foreign origins, ambiguous/skipped page numbers and unsupported cursor continuations fail the read. Exhausting the page budget leaves coverage incomplete. These readers cover the configured bounded inventory, not an unbounded historical export. See [GitHub pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api) and [GitLab pagination](https://docs.gitlab.com/api/rest/#pagination). Real provider pagination, retention and ACL behavior still require tenant acceptance.

```json
{
  "id":"latency", "name":"Auction latency", "selector":"VERIFIED_AGGREGATE_SELECTOR",
  "threshold":250, "operator":"gt", "unit":"ACTUAL_UNIT", "consecutive":3,
  "maxSampleAgeSeconds":180, "maxSampleGapSeconds":180
}
```

Verify actual units and selector behavior in the tenant. The threshold above is illustrative. Counts must be integers from 1–10; sample age/gap limits are 1–900 seconds. IDs are unique per service and invalid definitions fail at configuration load.

The connected example sets explicit operational limits. Defaults are 180 seconds for startup grace, polling freshness, and tick/poll duration; 300 seconds for queue age; and 1800 seconds for independent rollback verification. When maxPollAgeSeconds is omitted, its default is at least three poll intervals. Operational time limits support 1–86400 seconds. Tune them from measured workload and provider behavior. `operations.notify:false` disables proactive notices while retaining the read-only report.

## Local evidence

Provider `retryScope` labels opt the connected runtime into shared database-backed retry deadlines. Set the same label only for clients known to share the same provider account quota. Buckets also include the logical service tenant, provider family and canonical configured endpoint; different tenants/endpoints stay separate. Dynatrace API and logs can share a bucket at the same endpoint. Use `oauth.retryScope` separately for a token endpoint's quota, including its URL path. The connected example contains placeholder account labels to replace before use.

Committed Retry-After/rate-reset deadlines survive process replacement and are observed by other instances using that database. PostgreSQL uses database time. A later short response cannot reduce an existing hold. The store keeps a hashed bucket key, deadline, HTTP status and update time; it stores no token or client identity. A configured gate's storage failure blocks a new request. Without a label, or in the standalone read-check CLI without a runtime store, waits remain local to that client. This is reactive coordination after an observed response, not a proactive quota allocator; already in-flight requests cannot be recalled.

Rollback has its own token, optional OAuth configuration and explicit retry assignments. Reader OAuth and reader quota labels are not inherited. A held or locally unauthenticated deployment has zero deployment-transport calls and requires a fresh proposal/approval after correction. A failure after submission remains uncertain even if saving its observed retry deadline fails. Database restore retains waits committed in the snapshot; waits learned after the backup or lost before commit require external reconciliation.

For a prepared database restore, sre:restore retry-scopes inventories explicitly configured buckets, including disabled readers, without a database/provider call. The local retry-facts command accepts reviewed independent facts with original absolute deadlines and writes the maximum waits plus an idempotent receipt atomically. It retains the action hold and records providerVerified false. Keep affected readers disabled until that review/import completes. [The restore procedure](BACKUP-RESTORE.md#restore-independently-retained-retry-facts) covers scope binding, review freshness, file limits, release serialization and the limits of operator attestation.

### Integration counts by service

The console groups integration cards by configured service, with its key and environment. Each card counts retained source events for that service. One log-read event can contain many log records; replaying the same retained event does not increase the count. A zero count does not prove a reader failed, and historical events do not prove a reader is healthy. Read freshness and failure remain separate labels. A client without a scoped count displays unavailable rather than borrowing the database-wide total.

The header still reports the database-wide event total, including retained history from services removed from the current configuration. Those retired services do not receive current integration cards. A failed count read makes the status request unavailable; it does not manufacture zero counts. Counts are read-only history inspection and do not grant sharing, source access, QA or deployment authority.
