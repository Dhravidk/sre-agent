# Tracked MR and PR readers

The repository poller now follows already associated GitLab MRs and GitHub PRs as well as deployments. A missed update webhook no longer leaves a forward-fix branch pinned to its old head. This is a bounded reader in the existing single-worker runtime; it does not implement the proposed distributed dispatcher or discover every previously unseen MR.

Each metadata read confirms the requested resource twice. The connector checks the provider number, repository/project mapping, current head, source timestamp and state. A moving response is retried on a later poll. GitLab's diff references can be initially unavailable; contradictory current head/diff references are rejected. GitHub's pre-merge test merge SHA is not recorded as an actual merged commit. Provider field semantics follow the [GitLab MR API](https://docs.gitlab.com/api/merge_requests/) and [GitHub PR API](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request).

## Durable facts and fresh observations

The provider's `updated_at` is the source event time. The coordination clock records when the read began and completed. Polling an unchanged MR does not fabricate a new provider update or repeatedly invalidate its plan, QA result and investigation revision. A previously unknown base or merged commit can still add meaningful identity information.

Meaningful source facts enter the existing immutable event/change ledger. A checksummed `change-read:<service>:<provider>:<number>` checkpoint retains the latest scoped read receipt, CI visibility and any read error. MR/PR ingestion, its receipt, the optional GitLab pipeline event, incident revision and reassessment work commit in one SQL transaction. A failed CI write cannot expose a partial MR update or replace the last accepted pipeline status. Accepted CI carries its immutable source-event reference; reading a completed receipt validates that the referenced facts exist, match their hashes and agree on project, SHA, pipeline identity, status and source time. Standalone MR ingestion cannot mint an observed CI receipt. Earlier version-one CI receipts project as unknown until a fresh atomic read, without rewriting their saved history. A slower or older peer cannot replace a newer accepted read proof. Duplicate source deliveries cannot hide a competing equally timed identity: comparisons deduplicate identities before applying a bounded result window, and ambiguous heads remain unknown.

The reader selects the twenty least recently attempted active change references per service/provider. Each reference has its own ten-second transport deadline within the source batch budget. Unattempted references retain their priority when that batch budget expires. A failing reference does not keep later references from being attempted. Deployment inventory and tracked-change reads are attempted independently, so a deployment permission error does not suppress permitted MR reads; overall health still reports the incomplete coverage. Failed, missing, wrong-scope or stale receipts keep overall coverage incomplete. Freshness follows the operational polling-age setting. This is bounded operational behavior, not a throughput or production-capacity claim.

After restore or database transfer, old reader freshness is cleared. A successful new read can reaffirm an unchanged MR whose provider timestamp predates the restore, because its new read time is retained separately. A read that began before the restore generation cannot certify the new generation. Reaffirming a positive relationship remains explicit; a withdrawal stays in force.

## CI, code review and communication

GitLab's visible head-pipeline record is retained at its own SHA, status and update time. Missing permissions, missing timestamps, invalid clocks and a pipeline for an unrelated or synthetic commit remain unknown. A rejected parent MR read cannot publish its reported CI. Observed here means that the exact provider fact was saved; it does not mean a passing test result. One successful pipeline does not establish all checks, deployment or recovery. The metadata reader does not periodically collect all GitHub CI; existing CI webhooks and on-demand review checks remain separate.

A receipt retains what its MR read reported. The current view reconciles that report against saved facts for the same configured provider scope, project, pipeline and commit. A later transport read cannot make an older source version current. Equally timed contradictory statuses produce `unknown` with both source references; duplicate deliveries cannot hide the disagreement. Newer unambiguous provider versions resolve it. Different pipeline runs and different provider scopes stay separate. This concerns one visible run and never establishes that all checks passed.

The existing change ledger also records a checksummed scope/time projection at ingestion without changing the original inbox body or delivery hash. Historical reader events can prove their scope through their deterministic reader identity. Unqualified historical hooks do not acquire a new scope. The latest source versions are selected before bounding the history window; a long-running pipeline does not become permanently unknown merely because it has many progress updates. Reports without comparable versions are queried separately.

GitLab's [pipeline API](https://docs.gitlab.com/api/pipelines/#retrieve-a-single-pipeline) exposes update and finish times separately. Its [documented pipeline hook](https://docs.gitlab.com/user/project/integrations/webhook_events/#pipeline-events) can omit `updated_at` and carries the project at the top level. The host retains that ingestion scope and labels finish/create times as such. A contradictory hook without a comparable update version makes CI unknown until a sufficiently fresh scoped provider read reconciles it. Receipt time is never substituted for a provider update version.

CI visibility can disappear and return while the MR metadata and CI delivery identities stay unchanged. Such a meaningful transition now writes a host visibility event and reassessment work in the same transaction, only for current incident relationships. Concurrent readers lock that comparison; restore retains the established lock order. The event is a visibility observation, not an invented pipeline outcome. Host-derived CI state participates in notification decisions even if a reasoner returns unchanged prose. Joined teams receive changed understanding, while repeated status, read-time refreshes and duplicate reports stay quiet.

The worker collects associated forward-fix code at the latest unambiguous observed head, even when that MR is absent from the current deployment or bounded problem window. Source collection is bounded to ten persisted associations per investigation; further scope is reported as incomplete. Changes inform only active incident relationships and their authorized joined rooms. Acknowledgements, approval and independent recovery retain their existing boundaries.

The console and newly drafted Markdown tickets show source-update time, read time, CI visibility and its saved source reference separately. Bounded model context retains that reference as provider metadata; it is not an analysis evidence ID. The change timeline also retains code history sharing known commit identities; such history does not establish an incident relationship or common cause. The grouped history now makes that distinction explicit.

## Readable, bounded change history

The console, Teams `changes` reply and newly drafted Markdown tickets use the same history projection. Raw source facts remain in the database and in the bounded API `items` window. The grouped view shows provider, change/run identity, commit, recorded status, source-time kind, receipt time and source-event references. Repeated CI deliveries share a card while distinct status/time observations remain visible. Different known runs, commits, provider scopes and relationship meanings are separate. An unidentified run is labelled as reports that may cover multiple runs; it does not receive a latest CI status.

Only comparable update times participate in a card's latest update-version summary. A finish/create time is shown as a different kind of timestamp. Equally timed contradictory statuses remain conflicting. The summary concerns that card's bounded history, not current CI, all checks, deployment or recovery. Current tracked-read metadata stays visible separately.

Relationship labels distinguish a provider review, an explicitly linked change, a commit matching linked changes, a historical link awaiting reaffirmation, a withdrawn relationship, retained incident evidence and shared-commit background. An earlier or matching commit is not proof of cause or pipeline ownership. CI arriving after a relationship is withdrawn can remain visible as shared-commit history when the incident already knows the commit. It does not recreate the link or wake its former operational incident. Withdrawal references and restore qualifications remain visible.

The window reserves MR/PR observations by linked reference before filling with recent source events, so a CI delivery storm cannot evict the linked head. It is still bounded: at most 500 candidate facts, 200 reserved reference facts, twenty per reference, one hundred links and one hundred cards. Cards retain up to twenty-five source references for display, preferring distinct status/time observations before repeated deliveries. Coverage reports each bound, and counts describe this window rather than all provider traffic. Original inbox hashes and matching ledger identities are checked before facts are presented. Reading or grouping history does not change source facts, incident state or action authorization.

## Patch export correction

The native reader exercise found that the fixture QA adapter trimmed the final newline from its exported Git diff. Its saved branch and business checks were valid, but `git apply` rejected the exported patch. New exports preserve exact Git output bytes. A regression applies the stored patch to a clean checkout of the trusted source and compares the resulting bytes with the reviewed workspace.

Earlier saved results are not rewritten. The console flags a patch export missing its final newline. Regenerate it from the saved local commit before applying it, or request a fresh local QA run. This does not invalidate the historical business-test result or turn a local fixture run into production acceptance.
